# PLogIt - Process Log

> **What this is:** Structured process record for building PLogIt. One entry per build increment, plus entries for decisions and milestones worth remembering. Per Master Prompt Section 5.
> **Convention:** Chronological, oldest first. New entries append at the bottom.
> **Related artifacts:** [`PLogIt - Product Spec.md`](./PLogIt%20-%20Product%20Spec.md) (the bible), [`Master Prompt.md`](./Master%20Prompt.md) (constitution).
>
> **Naming note:** This file is the *build process* log. It is distinct from PLogIt's in-app "activity logs" (the pentester feature). Do not confuse the two.
>
> **Project note:** PLogIt was originally built as a university course deliverable. That framing is now retired. It is a personal project. Entries written before 2026-07-11 retain their original "talk note" / presentation-material commentary because that was the context at the time. Treat those as historical record, not current direction.

## Decisions

### 2026-07-06 · Decision - Product name
- Context: Needed a brandable, speakable name. Candidates were PLogIt, PLogEm, PLog, OpLog, CaseFile, RedLog, FieldNotes.
- Decided: **PLogIt** (PenTest Logging It).
- Alternatives weighed: PLogEm rejected (grammatically awkward, harder to say). PLog too generic. CaseFile/OpLog viable but PLogIt carries the action verb and fits purpose.
- Note: Retroactively logged. Confirmed in Q&A round 1.

### 2026-07-06 · Decision - Product scope (A1)
- Context: Whether PLogIt is an internal lab notebook, a client deliverable generator, or both.
- Decided: **Logs only for v1.** No findings object, no severity, no CVSS/CVE. PDF export is an evidence pack for a downstream auditor, not a client report.
- Alternatives weighed: Logs + Findings (recommended by advisor, rejected by user for v1 scope). Unified thing (rejected, too vague).
- Note: Retroactively logged. This is the load-bearing product decision. The reframing: PLogIt sits in a pipeline (Pentester to Auditor to Blue Team). Our job is thorough honest capture, and judgment is someone else's job.

### 2026-07-06 · Decision - Terminology (A2)
- Context: "Goal/Contract" used inconsistently in the original sketch.
- Decided: **"Engagement"** everywhere (industry standard, appears in pentest SOWs, PTES, PCI DSS).
- Alternatives weighed: Project (too generic), Assessment (clinical), Contract (too legal, confuses paper with work), Operation.
- Note: Retroactively logged.

### 2026-07-06 · Decision - Scale and deployment (A3)
- Context: Drives auth, MFA, encryption, multi-tenancy, legal exposure.
- Decided: **Any size, SaaS, hosted on user's own VPS.** SaaS is a hard project requirement.
- Alternatives weighed: Advisor recommended self-hosted first (lower liability, simpler MVP). User overrode: SaaS is the assignment constraint.
- Note: Retroactively logged. Honest note: SaaS means the user hosts sensitive pentest data (target IPs, creds, vulns) for others, which carries real legal/security liability. Mitigations baked into spec: strict sanitization (E3), audit log (E1), archive-never-delete (C3).

### 2026-07-06 · Decision - Review workflow (A4)
- Context: Original spec had a contradictory edit rule ("member edits X, but leader edits from next board"). Needed a clean model.
- Decided: **Full state machine.** `Draft → Submitted → Approved → Exported`. Members edit freely while Draft, locked once Approved, leader-only edit post-approval, and immutable once Exported. Rejection (Submitted → Draft) requires a mandatory comment.
- Alternatives weighed: Simple lock (rejected, too coarse).
- Note: Retroactively logged. Rejection comment is the *only* place comments exist in v1 (no general-purpose commenting).

### 2026-07-06 · Decision - Multi-tenancy model
- Context: Whether to add an Org/Account entity above User and Engagement for SaaS isolation.
- Decided: **No Org entity. Google Classroom model.** Anyone creates an Engagement and becomes its Leader. Members join via short codes (e.g., `PL0G-XXXX`). A user can be in many engagements across different leaders (contractor-friendly). Data isolation is by membership.
- Alternatives weighed: Org/Account layer (recommended by advisor for future-proofing). User chose Google Classroom model: lower signup friction, contractor-friendly, familiar. Org layer can be added later *above* engagements without reshaping the core if real firms demand firm-level admin.
- Note: Retroactively logged. Code-join always grants member role, never leader. Leader transfer is a separate explicit action (cannot orphan an engagement).

### 2026-07-06 · Decision - Tech stack locked
- Context: Assignment constraints, non-negotiable.
- Decided: Spring Boot backend, Hibernate (ORM), PostgreSQL, Spring Security, React + Vite frontend, GitHub Actions CI/CD with Trivy + Semgrep, deploy to VPS with SSL + domain.
- Alternatives weighed: Advisor suggested Next.js, rejected because backend is separate Spring Boot so Next.js's SSR/backend value is unused. Vite is the leaner fit for a SPA.
- Note: Retroactively logged. All items are MUST-follow per the assignment.

### 2026-07-06 · Decision - PDF purpose (D10 reframing)
- Context: What the exported PDF actually is, given logs-only scope.
- Decided: **Auditor-facing evidence pack.** Structure: cover page, scope/RoE summary, objectives, logs (chronological, with code blocks + images rendered), appendix (out-of-scope acknowledgements). Explicitly excludes severity ratings, CVSS, CVE refs, remediation advice, client branding. Those belong in the auditor's downstream report.
- Alternatives weighed: Client deliverable (rejected, that is the auditor's job). Internal audit plain dump (rejected as too thin).
- Note: Retroactively logged. This resolved the A1 tension cleanly: no findings object needed because judgment is not our stage.

### 2026-07-08 · Milestone - test_api.py caught a CSRF bug CI could not
- Context: Extended test_api.py to cover Slices 6 and 7 (log CRUD + state machine transitions). First run: 62 of 90 checks failed, every POST returned 403 Forbidden. Investigation revealed the backend NEVER emitted the XSRF-TOKEN cookie, so every state-changing request from a non-MockMvc client was rejected.
- Root cause (two compounding Spring Security 6 behaviors): (1) Deferred CSRF token loading. CsrfFilter only writes the XSRF-TOKEN cookie when the token is actually resolved during request processing. For a pure JSON API with no server-rendered form, nothing accesses the CsrfToken, so the cookie is never written. (2) Default XorCsrfTokenRequestAttributeHandler emits a BREACH-resistant masked token. Even if the cookie were written, the SPA reading the raw cookie value and sending it back as X-XSRF-TOKEN would be rejected. Our SecurityConfig called CookieCsrfTokenRepository.withHttpOnlyFalse() but did NOT switch the request handler. Half the config.
- Why CI missed it: CI backend tests use MockMvc's .with(csrf()) which synthesizes a valid token and bypasses the real HTTP cookie flow entirely. CI frontend is lint + build only, no live API. No test ever did a real POST over HTTP with cookie-based CSRF. The bug existed since Slice 3 and shipped through Slices 3-7.
- Fix: (a) Added CsrfTokenRequestAttributeHandler to SecurityConfig (raw token, JS-readable, not XOR). (b) Added a filter after CsrfFilter that force-resolves the deferred token (token.getToken()) and saves it via the repository, so the cookie is emitted on every response. Also fixed a second latent LazyInitializationException in EngagementController.listMine and JoinController.join (same bug class as Slice 6.5: DTO mapping in the controller after the transaction closed). Moved listMine and join-by-code into transactional service methods (listSummariesForUser, joinByCode).
- Learning / note: Strongest presentation material in the project. "My API test script caught a CSRF bug that the unit tests, integration tests, and CI all missed, because MockMvc bypasses the real HTTP cookie flow." This is the shift-left DevSecOps argument made real, and it validates the decision to write a real HTTP-level test script alongside the MockMvc suite. The two test layers are complementary: MockMvc proves logic, HTTP tests prove the real wire contract. Process change: test_api.py is now a third gate for any slice that touches auth or state-changing endpoints.
- Reference: SecurityConfig.java (csrf handler + force-resolve filter), EngagementService.java (+listSummariesForUser, +joinByCode), EngagementController.java (thinned listMine), JoinController.java (thinned join). test_api.py now 90 checks, all green. mvn test 33/33 (no regression).

### 2026-07-09 · Milestone - Tailwind directives bug caught (the invisible-app root cause)
- Context: During the overhaul, the user reported "I see no changes" after every restart and reload. Investigation revealed styles.css was missing the three Tailwind directives: @tailwind base; @tailwind components; @tailwind utilities;. Without them, the Tailwind PostCSS plugin has nowhere to inject generated utilities and emits nothing. The compiled CSS was 1.7 kB with ZERO utility classes (.flex, .bg-primary, .items-center all absent). The entire app had been rendering as effectively-unstyled HTML since Slice 2.
- Root cause: The directives were never added in Slice 2 (frontend scaffolding). Tailwind does not error when directives are missing. It silently generates nothing. So the build passed, ESLint passed, but no layout/styling utilities existed. The app "looked like it worked" only because raw HTML + the hand-written CSS variables (:root colors applied via body) produced a vaguely readable page.
- Why it was not caught sooner: My verification gates (build passing, ESLint clean) were inadequate for this failure mode. Tailwind's silent no-op on missing directives is a known footgun. The bug was invisible because the app was never truly "broken," just unstyled, and the bare HTML was close enough to readable that it passed casual visual inspection through 10 slices.
- Fix: Added the three @tailwind directives at the top of styles.css. Compiled CSS jumped from 1.7 kB to 18.2 kB (10x), now containing all utilities.
- Learning / note: Strongest presentation material of the overhaul. "The app shipped 10 slices with no Tailwind utilities generated because three lines were missing from styles.css, and nobody noticed because Tailwind fails silently and the raw HTML was barely readable enough to pass." This is a real DevOps/process lesson: a passing build does not prove the stylesheets work. Process change: after any CSS/Tailwind config change, verify the compiled CSS actually contains expected utility classes (grep for .flex in the built output), not just that the build exits 0. Logged as a standing rule in the Knowledge Base.
- Honest note: I chased browser-cache theories for two full turns before inspecting the compiled CSS pointed at the real cause. I should have grepped the built output the moment "no change" was reported, rather than assuming the server was correct. The anti-overclaiming rule applies to my own verification claims: "build passes" was true but meaningless here.
